# План разработки: веб-таблица «Тысяча»

Основа: [ТЗ v0.1](../tz-web-resource-1000.md). Окружение: Node 24, npm, git.

## Архитектура

Монорепозиторий на npm workspaces:

```
web-1000/
├─ packages/core      — ядро подсчёта: чистый TypeScript, без зависимостей (сервер + клиент)
├─ apps/server        — Fastify + Socket.IO + Drizzle/SQLite (better-sqlite3)
├─ apps/web           — React + TypeScript + Vite
│  └─ public/icons    — SVG-заглушки символов (bolt.svg, barrel.svg, …)
└─ docs/              — план, решения по правилам, деплой
```

Ключевые решения:

- **Ядро = функция `replay(game, events) → GameState`.** На вход: состав и порядок мест, первый раздающий, упорядоченный список записей (кон или событие раздачи). На выход: счёт по каждой строке, болты, бочка и попытки, очерёдность (раздаёт / сдвигает / на 100 / на прикупе), символы для ячеек, победитель. Никакого хранимого состояния: правка прошлого кона = повторный `replay`.
- **Валидация входа** — zod-схемы на сервере (REST/сокеты); core без зависимостей, бизнес-проверки кона — `validateHand` в core.
- **Тесты** — пишутся только по отдельной просьбе (решение 19.10.2026, отступление от п. 9.1 ТЗ). Проверка: typecheck, lint, ручной прогон сценариев.
- **Сервер** — источник истины. REST: комнаты, игроки, партии, статистика. Socket.IO: комната канала `game:<id>`, полный снимок при подключении, дальше события `state` после каждого изменения.
- **Права** — без паролей: `playerId` из localStorage, сервер проверяет, что игрок в партии / является ведущим. Зритель (ТВ) — отдельный read-only код в ссылке.
- **Кеш** — вычисленное состояние партии храним в памяти/таблице-кеше, инвалидируем при любом изменении.

## Этапы

### Этап 0. Каркас (≈0,5 дня)

- git init, npm workspaces, общий tsconfig, ESLint + Prettier.
- Пустые пакеты core / server / web, скрипты `dev`, `build`, `typecheck`, `lint`.
- **Готово, когда:** `npm run typecheck`, `npm run lint`, `npm run build` и `npm run dev` работают из корня.

### Этап 1. Ядро подсчёта (≈3–4 дня) — главный этап

1. Модель данных ядра: `Seat`, `Hand` (кон), `DealEvent`, `PlayerInput`, `GameConfig`, `GameState`, `RowResult`.
2. Очерёдность: раздающий, сдвигающий, игрок на 100, на прикупе (2/3/4 игрока), переход после штрафов.
3. События раздачи (2.3): счётчики девятки при сдвиге и пересдач, неправильная раздача, −120.
4. Подсчёт кона по шагам 3–8 алгоритма: заказавший, соперники, прикуп, роспись (треть / половина), тёмная (×2 после округления, марьяжи без удвоения), проверка суммы 120.
5. Болты: счётчик, каждый третий −120.
6. Бочка (шаг 9): посадка ровно на 880, очки только со своей ставки, 3 попытки, кон на прикупе не считается, падение 880 − ставка, ставка < 120, штрафы на бочке, второй садится → первый −120, несколько сразу → каждый −120.
7. Бульдозер, победа, золотая тысяча.
8. Символы ячеек (▲ ▼ Р ◐ • ▣n ↓ ⌀ ↻ ✂ ✕ П ★ ♔) как данные, а не строки.
9. Проверка: прогон примера из 7.1 и пограничных случаев из 9.1 скриптом, сверка с ручным расчётом.

- **Готово, когда:** все правила разделов 2–3 и R1–R6 реализованы, пример 7.1 считается верно.

### Этап 2. MVP (≈4–5 дней)

1. **БД (Drizzle):** rooms, players, games, game_players, hands, hand_inputs, deal_events, edit_log. Миграции.
2. **REST:** создать комнату / открыть по коду, пул игроков (поиск, создание, уникальность имени), создать / продолжить / завершить / отменить партию, передать роль ведущего.
3. **Socket.IO:** подписка на партию, действия (событие раздачи, итог торгов, ввод игрока, подтверждение кона), рассылка состояния. Порядок применения — очередь на партию.
4. **Web:**
   - Главная: создание комнаты → ссылка.
   - Вход: имя с автодополнением, «Это не я», запоминание в localStorage.
   - Комната: список партий, создание партии (выбор 2–4 игроков, порядок мест, первый раздающий, ведущий).
   - Экран кона по этапам (раздача → торги → ввод → ожидание), постоянная плашка «мой счёт / болты / бочка».
   - Режим ведущего: сводка ввода, проверка 120, ввод за других, «Подтвердить кон», «Неправильная раздача».
   - Таблица на телефоне (пока текстовые символы).

- **Готово, когда:** партия на 3 телефонах проходит от создания до победы, таблица обновляется у всех без перезагрузки.

### Этап 3. ТВ, символы, правка (≈2–3 дня)

- Ссылка зрителя, раскладка 1920×1080, крупный шрифт, текущее состояние кона над таблицей, легенда справа.
- SVG-заглушки в `apps/web/public/icons/<event>.svg`, цвет по смыслу, подмена файлом без правки кода.
- Переключатель «марьяжи под числом».
- Детали ячейки по нажатию: сырые очки, марьяжи, кто ввёл, правки.
- История конов, правка подтверждённого кона, пересчёт, журнал правок (было / стало / кто / когда).

### Этап 4. Статистика (≈3 дня)

- Срезы: партия, комната за всё время, игрок; личные встречи.
- Группы показателей из раздела 8 (итоги, заказы, тёмные, игра соперником, марьяжи, штрафы, бочка, бульдозеры, рекорды) — считаются в core из тех же `replay`-результатов.
- График хода партии (счёт по конам), показ на ТВ после завершения.

### Этап 5. Улучшения и деплой (≈2 дня)

- PWA (manifest, service worker), экспорт партии (CSV/JSON), тёмная тема, настройка символов.
- Деплой: сборка, pm2/systemd, конфиг nginx с проксированием WebSocket, Let's Encrypt, ежедневный бэкап SQLite (cron + `sqlite3 .backup`), инструкция в `docs/DEPLOY.md`.
